# Rightsize Database Discovery

How to find every CNPG `Cluster` and MariaDB `MariaDB` CR across the estate when a filesystem grep of the workload repos returns nothing.

## The problem

CNPG and MariaDB CRs are frequently not source YAML in the workload repos. They are generated by Pulumi or Kustomize and land as rendered manifests in the per-cluster argocd repos under `1-manifest/` directories, so `grep -rl 'apiVersion: postgresql.cnpg.io'` across the workload checkouts misses them.

## Discovery method

### Step 1: scan ArgoCD application images

Paginate the applications with `argocd-kilic__list_applications(limit=50, offset=N)` and inspect `status.summary.images` for database signals:

- CNPG operator on the cluster: `ghcr.io/cloudnative-pg/cloudnative-pg:<version>`.
- CNPG instance in the app: `ghcr.io/cloudnative-pg/postgresql:<major>`.
- MariaDB operator on the cluster: `ghcr.io/mariadb-operator/mariadb-operator:<version>`.
- MariaDB instance in the app: a `mariadb` image from the MariaDB registry.

### Step 2: check out the workload repo

For each app that shows database images, use its normal workload clone. If an isolated checkout is needed, create one per `command-wt`.

### Step 3: read the CR specs

Look in `.deploy/<cluster>/postgresql/db.yaml` (CNPG) or `.deploy/<cluster>/db/mariadb.yaml` (MariaDB). Extract `metadata.name`, `spec.instances`, and check `spec.monitoring` (CNPG) or `spec.metrics.enabled` (MariaDB).

## Pitfalls

- Broad semantic or organization-wide code search is the wrong tool for this: the scan times out before it covers the tree, and the CRs it would need to find are not in the repos it searches. ArgoCD image scanning is the reliable path.
- `gitlab__search_group_code` requires a `scope` parameter that its tool description omits, so a call written from the description alone returns a scope error.
- Per-cluster argocd worktrees carry generated manifests that lag the source. Read the CR specs from the workload source repos, not from the argocd manifest repos.
